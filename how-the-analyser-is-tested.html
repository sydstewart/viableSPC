How the StepChange Analyzer is tested

We work to make the analyser dependable, and to be open about how. This page explains how it is checked before each release, and what testing can and cannot tell you.

A published method

The analyser uses Bootstrap CUSUM change-point analysis, as described by Wayne Taylor (2000), building on work by Page, Hinkley, and Efron and Tibshirani. Where the analyser deliberately differs from the published description, the difference is recorded and explained.

An independent cross-check

A second implementation of the method was written separately, from the published description rather than from the analyser’s own code. Given the same data and settings, it produces exactly the same results as the analyser on classic datasets used in the statistical literature: the annual flow of the River Nile and British coal-mining disasters. On both, the analyser finds the changes that published studies of these datasets report.

Automated checks before every release

A suite of automated tests runs before every release. It checks how files are read (number styles, date formats, gaps), the calculations, the random shuffling the method relies on, the displays and exports, and the whole analyser page working together in a simulated browser.

Every change is tried on a separate copy first and released only when the tests give the expected results. When a problem is found, a test is added for it, so it cannot quietly return.

Looking for what could go wrong

Each stage of the analysis, from reading a file to presenting a result, has been reviewed systematically for the ways it could produce a wrong, missing or misleading result, using failure mode and effects analysis. Risks are prioritised by how serious they would be, and the most serious are dealt with first. The review is kept up to date as the analyser changes.

Learning from real data

Real files find problems that test data can miss. For example, a monthly file once produced a false warning of many missing months because dates were being read in two different ways. The cause was fixed, and a test now checks for it.

Results you can reproduce

Every result records its seed, the settings used, a fingerprint of the data analysed and the analyser version. Anyone with the same file can enter the seed and reproduce the result exactly. Reproducing a result.

Careful change control

Every change is kept under version control, so each release can be traced, and each release is described in the release notes.

Your data stays with you

The analysis runs entirely in your web browser. Your file is not uploaded to our servers.

What testing cannot do

Testing reduces the chance of errors; it cannot rule them out. The method also rests on assumptions, such as each stage having a stable average and neighbouring values not being strongly related. When those do not hold, results can mislead even when the software works exactly as intended. Checking your StepChange results explains what to look for.

Results support your judgement; they do not replace it. The analyser is for process improvement and the retrospective analysis of historical data, and it is not a medical device. Intended use.

Who develops it

The StepChange Analyzer is developed by a Chartered Chemical Engineer with long experience of CUSUM and statistical process control, first in industry and later in services.

Found something unexpected?

If a result looks wrong, or the analyser does something you did not expect, please tell us through the feedback form. Reports help us improve the analyser and its tests.
